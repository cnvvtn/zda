## ✨ Redefining Knowledge Acquisition

**ZDA is your AI knowledge architect.**

Try giving it an imaginative or demanding question:
* *Why can't even light escape a black hole?*
* *What is the Byzantine Generals Problem really about?*
* *Why does procrastination make you feel more exhausted?*
* *Why is the A\* pathfinding algorithm so fast?*

It will not hand you a long, professional-looking, sleep-inducing essay. Instead, it becomes a **storyboard director** that breaks down your question with precision: what suspense to introduce first, when to pause, which sentence deserves highlighted subtitles, and which scene should cut into motion.

The final result is an **immersive, playable dynamic view** with smooth HTML animation, precise timelines, narration, dedicated share links, and even one-click recording into a finished video.

In an age where information is easy to obtain, truly understanding it remains painfully difficult. Search engines give you links, large models pile up text, and video platforms feed you fragments. The conclusion may exist, but the **path to understanding is broken**.

ZDA turns dull text piles into a smooth view flow:

| Traditional Problem 😩 | Real Feeling | ZDA Solution 💡 |
| :--- | :--- | :--- |
| **Bookmarks gather dust** | Long articles are hard to digest. Bookmarking feels like learning, and screenshots feel like review. | **Knowledge slicing**: Dynamic storyboards and concise subtitles bring the knowledge directly to you. |
| **AI reads like a manual** | A screen full of dry text leaves no impression after reading. | **Concept visualization**: Text becomes a dynamic playback flow with sound and visuals. |
| **Science content is costly to make** | Finding materials, writing scripts, editing, and voiceover work all take too much effort. | **Industrial-grade output**: Scripts, timelines, narration, and visual construction are handled automatically. |
| **Hard topics are hard to enter** | You want to learn, but cannot find a starting point and give up after two lines. | **Cognitive ramp**: Start from a question and follow a smooth path from basic intuition to deeper understanding. |
| **Generation is a black box** | You wait on a progress bar with no idea where it is stuck. | **Transparent progress**: Review, generation, audio, assembly, and every major step are visible in real time. |

## 🛠️ Lightning-Fast Local Engine

Want to run the generation pipeline locally? Prepare MySQL, model/TTS configuration, and runtime secrets, then start the service.

### 1. Initialize the Database
The project depends on MySQL 8.0. Make sure a local or remote service is available:
```text
Default connection: 127.0.0.1:3306/zda

```

*Note: Database SQL is not published with the source code. Make sure your table structure is consistent with the mappings in `app/db/models.py`.*

### 2. Inject Core Configuration

The main configuration file is `app/config.yml`.<br>For security, sensitive keys are loaded dynamically from the database:

```yaml
# Core key-value entries that need to be configured in the database
dynamic_view_model_profile.api_key: "Your model API key"
website_content.content_key: "Your runtime secret bundle" # Includes payment, email, login signature, and related secrets

```

### 3. Build the Runtime Environment

Install the core dependencies in one step:

```bash
pip install fastapi uvicorn sqlalchemy pymysql pydantic pyyaml httpx python-multipart langchain-core langchain-openai openai google-genai dashscope paho-mqtt

```

### 4. Start the Service

Start through the Python module or Uvicorn:

```bash
# Option 1: Python module
python -m app.main

# Option 2: Uvicorn ASGI server
uvicorn app.main:app --host 0.0.0.0 --port 5000

```

### 5. Health Check

After the service starts, verify the health endpoint:

```bash
curl http://127.0.0.1:5000/health

```

**Expected response:**

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "status": "ok"
  }
}

```

## 🧭 Technical Framework Guide

If you want to do more than just run the service and quickly understand how ZDA connects models, payments, recommendations, and generation into a product pipeline, start with the backend entry point. The project is built with FastAPI, SQLAlchemy, MySQL, and Pydantic. `app/main.py` manages the application lifecycle, route registration, and scheduled tasks. `app/db/models.py` maintains the core table mappings, and `app/config.yml` provides a local runtime configuration example.

Model recommendations and model tiers are not hard-coded into the frontend. They are driven by runtime configuration such as `dynamic_view_model_profile`, then delivered to the page through `/api/website/generation-models`. You can understand `experience`, `basic`, `advanced`, and `top` as generation entry points with different quality and cost profiles. Each tier can bind to different models, nodes, prices, and Credit consumption.

The main Dynamic View generation pipeline lives under `/api/dynamic-view` and `app/features/dynamic_view/`. A single generation is split into topic review, storyboard scripting, HTML assembly, TTS audio, archiving, and playback stages. The frontend can poll progress or cancel tasks. When a task fails or is canceled, Credits are refunded according to the generation state.

The payment side has built-in ZPAY integration through `/api/payments` and `app/services/zpay_payment_service.py`. This pipeline covers order creation, order queries, asynchronous notification signature verification, notification rate limiting, MySQL distributed locks, and membership entitlement issuance, making it suitable for package purchases or compute-credit top-ups.

Credit is ZDA's internal compute settlement unit and is handled by `app/services/credit_service.py`. Daily grants, payment recharge, redemption codes, generation deductions, failure refunds, and expiration cleanup are all recorded in the ledger, making model usage cost traceable.

Official website content recommendation and display scheduling are handled by `website_topic_batch_service` and `website_universe_service`. The backend periodically generates recommended topics, refreshes official website topic batches, and recalculates "universe" showcase data by Dynamic View category so the homepage content stays fresh.

Real-time interaction uses MQTT and `/api/chat` for discussion initialization, session management, message delivery, and bullet-comment style interaction. Different environments can be isolated with `mqtt.topic_prefix` to prevent development, test, and production messages from mixing.

### Model Configuration Recommendations

Model capabilities are controlled dynamically through the `dynamic_view_model_profile` table instead of being hard-coded. At minimum, prepare the following nodes:

| Node | Typical Role | Recommended Configuration |
| :--- | :--- | :--- |
| `node1` | Topic understanding, content structure, main script generation | Use a stable text model with strong reasoning ability to prioritize structured output quality. |
| `node2` | HTML and animation segment generation | Use a model with stronger coding ability to turn storyboards into playable views. |
| `analyze` | Topic review and intent analysis | Use a lower-cost but stable model to reduce the cost of preliminary judgment. |
| `metadata` | Lightweight information such as summaries, titles, and tags | Use a cost-efficient model to improve overall throughput. |
| `tts` | Text-to-speech synthesis | The current pipeline reserves DashScope TTS configuration and can be replaced or extended as needed. |

### Payment and Entitlement Configuration

ZPAY is disabled by default. Before enabling it in production, complete `app/config.yml` and the database secrets:

```yaml
zpay:
  enabled: true
  pid: "Your ZPAY merchant ID"
  gateway: "Your ZPAY gateway URL"
  public_api_base_url: "Your public API base URL"
  plan_catalog:
    experience:
      name: Light Top-up
      money: "5.00"
      days: 1
      credit_total: 160
      model_level: experience
      priority_level: 1
```

```text
runtime_secrets.ZPAY_KEY: "Your ZPAY merchant secret"
```

It is recommended to first verify the full low-value flow of "create order -> payment callback -> signature verification and ledger entry -> Credit issuance -> model deduction", then gradually open higher model tiers.

## 🔌 Core Architecture and API Overview

The system is split into clear business-module routes:

| Route Prefix | Module Responsibility | Core Capabilities |
| --- | --- | --- |
| `/health` | **Probe** | Node health checks and liveness confirmation. |
| `/api/dynamic-view` | **Engine Core** | Create view generation tasks, poll progress, play HTML, and read audio/comment streams. |
| `/api/website` | **Frontend Aggregation** | Homepage gallery configuration, topic batch scheduling, model option delivery, and generation session management. |
| `/api/auth` | **Security Authentication** | Identity authentication, email verification-code issuance, and verification. |
| `/api/payments` | **Asset Hub** | ZPAY order creation, payment callback handling, entitlement issuance, and compute Credit settlement. |
| `/api/chat` | **Real-time Communication** | MQTT channel initialization, long-connection session list management, bullet comments, and message delivery. |
| `/api/admin` | **Admin Control** | System-level resource scheduling and global data inventory. |

## ⏱️ Automated Scheduling (CRON)

ZDA does more than respond to frontend requests. The backend includes robust scheduled maintenance, using MySQL `GET_LOCK` to guarantee singleton execution across multiple workers:

* **Zombie task recovery**: On service startup, historical unfinished pending tasks are automatically marked as failed so the frontend does not spin forever.
* **Asynchronous dispatch**: According to the configured interval, the backend periodically consumes and dispatches view generation tasks from the queue.
* **Quota reset**: Expired Credits are automatically cleared every day at `00:00 (UTC+8)`.
* **Content refresh**: Official website topic batches are refreshed every day at `00:00 (UTC+8)`, and universe recommendation data is recalculated every 6 hours to keep frontend content alive.
